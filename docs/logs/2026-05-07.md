## 关键设计决策

### D1：memory_candidates 纳入 Phase 0.5

原计划推迟到 Phase 1。修订：Phase 0.5 建立最小表结构，立住 candidate-only 数据模型。resolver 可暂缺，但 AI 提取必须先落 candidates 表。

**Why:** 不先建 candidates 表，AI 直写 memories 的问题就无法在 Phase 0.5 消除。

### D2：idempotency_key 使用 partial unique index

```sql
CREATE UNIQUE INDEX ON memory_events(source_type, idempotency_key)
WHERE idempotency_key IS NOT NULL;
```

**Why:** 单列 UNIQUE 会导致不同 source_type 的相同 key 冲突（例如健康数据和聊天消息恰好用了相同的幂等键）。

### D3：memory_type DEFAULT 'legacy'

`memories.memory_type` 列已存在（v3.3，值为 fragment/daily_digest/digested）。Phase 0.5 将 DEFAULT 改为 'legacy'，旧值视为 legacy 语义，新写入用 CONTEXT.md 分类法（identity_fact/preference/project_state 等）。

### D4：actor_scope 默认值有意义

`memories.actor_scope` 默认 `'{local_bot,claude_mcp}'` 而非空数组。**Why:** 空数组在权限检查时行为不确定，默认值应反映当前系统的实际 actor 集合。

### D5：memory_access_log 兼容未来 UUID memory_items

```sql
legacy_memory_ids INT[] DEFAULT '{}',   -- 当前 memories.id
memory_ids        UUID[] DEFAULT '{}',  -- 未来 memory_items.memory_id
```

**Why:** Phase 1 引入 memory_items 后 ID 类型会变成 UUID，提前分离避免 log 表破坏性迁移。

### D6：core_blocks 唯一约束 + active 索引

```sql
UNIQUE (block_key, version_no)

CREATE INDEX ON core_blocks (block_key, version_no DESC)
WHERE superseded_at IS NULL AND approval_status = 'approved';
```

**Why:** 防止重复版本号写入；active block 查询是热路径，需要 partial index。

### D7：函数命名 create_core_block_version()

原方案 `upsert_core_block()` 暗示原地覆盖。改名为 `create_core_block_version()`，明确每次调用都产生新版本。

### D8：不承诺零停机

定性为 **low-risk additive migration**，但执行前必须 `pg_dump` 备份。所有改动使用 `ADD COLUMN IF NOT EXISTS ... DEFAULT` 和 `CREATE TABLE IF NOT EXISTS`，不删列，不重命名。

### D9：Phase 0.5 的 AI 写入兼容策略

- AI/MCP 调用仍走现有 `save_memory()` 接口，不破坏
- 但必须同时写 `source_trust='assistant_inferred'`
- 同步产生 `memory_events` 记录 + `memory_candidates` 记录
- `assistant_inferred` candidate 不自动提交（status='pending'），Phase 1 再实现 resolver
