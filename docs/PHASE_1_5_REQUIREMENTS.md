# Phase 1.5 Candidate Review Policy & Short-Term Observation Layer — Requirements Document

> **Status**: Requirements / design planning. Do not implement.
> **Dependency**: Phase 1.4 Memory Items Retrieval Bridge must be sealed before any Phase 1.5 implementation begins. (Phase 1.4 tag: `phase-1.4-memory-items-bridge`.)
> **Last updated**: 2026-05-09

---

## 1. Motivation / Problem Statement

### Current pain point

Every candidate generated by the AI extraction pipeline goes through the same review flow: `pending` or `pending_auto` → `requires_review` or `committed`. This treats all candidate types as equivalent, creating three problems:

1. **Review burden**: Ordinary feelings, complaints, passing thoughts, and low-risk factual notes all enter the same manual review queue. The user must explicitly reject transient chatter that should never have required human attention.

2. **Emotional over-commitment**: A single emotional expression ("I feel terrible today") can be extracted as a candidate, flagged for review, and — if approved — permanently committed as memory. The system treats a transient emotional state the same way it treats a durable life fact.

3. **No digest pathway**: Repetitive low-signal observations accumulate as individual candidates. There is no mechanism to aggregate "user mentioned stress 5 times in 2 weeks" into a single digest while discarding the raw fragments.

### What Phase 1.5 addresses

Phase 1.5 introduces a **review policy classifier** that routes candidates into different channels based on their content type, durability, risk, and recurrence. It also introduces a **short-term observation layer** (VISION.md layer 2) as a temporary holding area for content that should not bypass review but also should not be permanently committed without pattern evidence.

## 3. Channel Taxonomy

Five review policy channels, from lowest to highest human involvement:

### Channel 1: `short_term_auto_write`

- **Action**: Write to a short-term observation buffer. Do NOT write to `memory_items` or `memories`.
- **Auto-expiry**: 7-14 days (configurable).
- **Digest path**: Eligible for periodic aggregation into Layer 3 summaries.
- **Examples**:
  - "我想她了" (I miss her)
  - "我现在很难受" (I feel terrible right now)
  - "这件事让我自我否定" (This makes me doubt myself) — emotional_observation only
  - "今天好累" (So tired today)
  - "天气真好" (Nice weather)
- **Excluded**: Health-derived mood inference, personality diagnosis, relationship fact inference, third-party source claiming user identity/personality/preference.

### Channel 2: `medium_factual_auto_commit`

- **Action**: Auto-commit to `memory_items` + `memories` with provenance, moderate importance (5-7). `source_trust` depends on the source: `user_direct` / `user_confirmed` for user-stated grades, course status, project facts, and technical environment. `system_generated` is reserved for trusted system facts (internal project state, verified `health_observation_summary`, etc.). `assistant_inferred` and `third_party_doc` should not auto-commit user identity, preferences, grades, relationships, or personality facts.
- **Review**: No manual review required. Written with `confidence` metadata.
- **Examples**:
  - "CSC165 51, STA237 68" (course grades)
  - "用户正在学习 Rust" (user is learning Rust)
  - "Arch Linux + i3 工作环境" (technical environment)
  - Project states: "正在搭建 n8n workflow"
- **Guardrails**: Factual, durable (>weeks), useful for future retrieval, low identity risk.

### Channel 3: `digest_to_long_term`

- **Trigger**: Periodic maintenance job (weekly recommended).
- **Group by**: Topic, person, domain, emotional category.
- **Threshold**: Count >= 3 related short-term observations OR cumulative importance above configurable threshold.
- **Output**: A digest *candidate* — NOT a direct `memory_items` commit. Digest candidates enter the review queue with `status=requires_review` or a new `batch_review` status.
- **Example inputs** (3+ short-term observations about work stress) → **digest candidate**: "用户在 3 月第 2-3 周多次提到工作压力，主要来源为 deadline 焦虑"
- **Example inputs** (5+ observations about missing Ellie) → **digest candidate**: "用户在过去两周内多次表达对 Ellie 的思念，频率高于此前观察期"

### Channel 4: `manual_review`

- **Action**: Existing review queue flow — candidate enters `pending` or `requires_review`.
- **Reserved for high-risk durable facts**:
  - `identity_fact` memory type
  - Hard relationship facts ("用户和 Ellie 分手了")
  - `health_baseline` / `health_pattern`
  - `risk_flag` / `policy_rule`
  - Financial/legal sensitive facts
  - `core_blocks` updates
  - Long-term personality/relationship/health inferences ("用户长期因为 Ellie 自我否定")
- **Never auto-committed**.

### Channel 5: `auto_reject_or_expire`

- **Action**: Silently discard or auto-reject.
- **Criteria**: Duplicate of recently committed memory, confidence below threshold, or content type explicitly excluded from memory extraction.
- **Examples**:
  - Duplicate factual observation within 24h.
  - "用户学习能力差" — inference about stable capability, not an observable fact. Auto-reject; never auto-commit.
  - Third-party source claims about user identity, personality, or preferences — auto-reject; the user is the sole authority on who they are.
  - Malformed or empty candidate.
  - Expired short-term observation not selected for digest.

## 4. Layer 2 Input Scope

### Initial scope (Phase 1.5)

- **Source**: Telegram/chat user-authored emotional expressions only.
- **Explicitly excluded**:
  - **Apple Health `stateOfMind`** — sensor-derived or self-reported mood from Health Auto Export.
  - **Sleep quality** — derived from sleep analysis data.
  - **HRV / heart rate** — sensor-derived physiological data.
  - **Any sensor-derived health anomaly** — belongs to health pipeline, not emotional observation pipeline.
  - Voice tone analysis.
  - Unprompted AI inference of emotional state from neutral text.
  - Any content where the user did not explicitly express an emotional state.

### Why exclude health-derived mood inference

Health data is sensor-derived signal. It cannot be mixed with user-authored emotional expressions in the same observation policy. A user saying "I feel anxious" and an Apple Watch reporting elevated HRV are fundamentally different evidence types. Cross-domain inference (health → emotion) requires a separate health-emotion policy and review gate — deferred to a future health-specific phase, not the candidate review pipeline.

## 5. TTL Policy for Short-Term Observations

| Signal level | Default TTL | Max without digest |
|-------------|-------------|---------------------|
| Low signal (importance < 4) | 7 days | 14 days |
| Medium signal (importance 4-6) | 14 days | 30 days |
| High signal (importance >= 7) | Channel to manual_review, not short_term | N/A |

After TTL expiry without digest promotion, the observation is deleted or archived. The raw event in `memory_events` remains for provenance but is not retrievable as active memory.

## 6. Layer 2 → Layer 3 Digest Policy

### Trigger

Independent weekly maintenance job. Does NOT integrate with Dream, does NOT use Telegram `job_queue`. Proposed script name: `scripts/consolidate_short_term_observations.py`. Run interval: 7 days (configurable).

### Grouping dimensions

- **Topic/domain**: work, study, relationships, health, projects.
- **Person**: specific individuals mentioned across observations.
- **Emotional category**: anxiety, frustration, sadness, joy, uncertainty.
- **Temporal cluster**: observations clustered within the same time window.

### Promotion threshold

At least one of:
- Count >= 3 related short-term observations in the digest window.
- Cumulative importance score above configurable threshold.

### Output format

A digest *candidate* (not a direct commit) with:
- `memory_type`: `emotional_trend` or `observation_digest`
- `source_event_ids`: references to all contributing short-term observation events
- `rendered_text`: Human-readable summary of the pattern
- `confidence`: Derived from observation count, consistency, and temporal spread
- `status`: `requires_review` (or new `batch_review` status)

## 7. Review Policy Classification — Decision Dimensions

Each candidate is evaluated across the following dimensions before channel assignment:

| Dimension | Type | Description |
|-----------|------|-------------|
| **factuality** | boolean/scale | Is this an observable fact or an inference? |
| **durability** | scale (hours / days / weeks / years) | How long is this likely to remain true? |
| **usefulness** | scale | Will retrieving this in 6 months help the user? |
| **risk** | scale | What is the harm if this is wrong? |
| **source_trust** | enum | `user_direct` / `user_confirmed` / `assistant_inferred` / `system_generated` / `third_party_doc` / `unknown` |
| **recurrence** | count or boolean | Has this pattern been observed before? |
| **privacy_level** | enum | `public_like` / `personal` / `sensitive` / `restricted` / `sealed` |
| **stability** | scale | Is this likely a transient state or a stable trait? |

Channel routing logic (simplified):

```
if risk == HIGH or durability == YEARS:
    → manual_review
elif factuality == LOW and durability <= DAYS:
    → short_term_auto_write
elif factuality == HIGH and durability >= WEEKS and risk <= MEDIUM:
    → medium_factual_auto_commit
elif recurrence >= THRESHOLD:
    → digest_to_long_term
else:
    → manual_review (conservative default)
```

## 8. Proposed Resolver Integration

### `classify_candidate_review_policy(candidate) -> ReviewDecision`

A new function (or integrated into `resolve_candidate` as a pre-step) that:

1. Receives a candidate before status assignment.
2. Evaluates decision dimensions.
3. Returns a `ReviewDecision` with `channel`, `confidence`, and `rationale`.
4. The existing `resolve_candidate` flow then acts on the decision.

### Channel actions

| Channel | Resolver action |
|---------|----------------|
| `short_term_auto_write` | Write to short-term observation buffer; do NOT call `insert_memory_item` or legacy `save_memory` |
| `medium_factual_auto_commit` | Call `resolve_candidate(force_commit=True)` with elevated confidence |
| `digest_to_long_term` | Create batch digest candidate with `requires_review` status |
| `manual_review` | Existing flow: `pending` / `requires_review` |
| `auto_reject_or_expire` | Mark candidate `rejected` with reason |

### Initial deployment: dry-run only

Phase 1.5-M2 classifier should run in **dry-run mode**: classify candidates, log decisions, but do NOT change any write behavior. This allows validation of the classification logic against real data before enabling any auto-commit or short-term observation pathways.

## 9. Schema Open Questions

The following schema decisions are unresolved and must be addressed during Phase 1.5 design (M1):

1. **`retrieval_tier`** — does not currently exist on any table. A new column may be needed on `memory_candidates` or `memory_items` to distinguish retrieval priority. Proposed values: `transient` / `low` / `default` / `elevated` / `always`. Short-term observations and low-signal digests would use `low` or `explicit_only` (never injected into chat context, only retrievable by explicit search). `restricted`/`sensitive` content may default to `explicit_only` regardless of other dimensions.

2. **`digest_pending` status** — does not currently exist. Candidates awaiting batch digest aggregation need a status that prevents them from appearing in the standard review queue while remaining queryable for the digest job.

3. **Short-term observations table** — does not currently exist. Options:
   - New `short_term_observations` table with TTL, source_event_ids, emotional_category, etc.
   - Extend `memory_candidates` with `review_channel` and `expires_at` columns.
   - Extend `memory_events` with TTL and channel metadata.

4. **`memory_events` TTL** — `memory_events` has no `expires_at` or `ttl_days` column. Short-term observation events need expiration.

5. **New table vs extend `memory_candidates`** — tradeoffs:
   - New table: clean separation, no risk to existing candidate flow, but adds schema surface.
   - Extend `memory_candidates`: reuses existing review queue, but risks polluting the candidate table with high-volume transient data.

6. **Digest output status** — should digest candidates use existing `requires_review` or a new `batch_review` status? `batch_review` would allow the review queue to group related digest items.

These are deferred to M1 design — no implementation decisions are made here.

### 10.1 M2 Classifier Limitations

The M2 `classify_candidate_review_policy()` is a **rule-based baseline** only. It uses type gates, source_trust gates, provenance gates, and simple keyword/pattern matching. It is suitable for validating the policy skeleton and testing gate ordering. It is **not a production-grade semantic classifier**.

**Current limitations**:
- Keyword/pattern matching is brittle, especially for Chinese emotional expressions.
- Durable emotional claims ("长期自我否定") cannot be reliably detected by fixed keywords alone.
- Negative inference patterns ("学习能力差", "学不会") may miss implicit or indirect wording.
- The distinction between ordinary feelings and hard relationship facts requires semantic judgment beyond current rules.
- Academic facts vs. ability/personality attribution require semantic judgment beyond current rules.
- `third_party_doc` handling is gated on `source_trust` but the field value depends on upstream extraction accuracy.

**Production enablement constraint**: Before any automatic write behavior is enabled (M3 observation_only, M4 medium_factual_auto_commit), Phase 1.5 must add and evaluate an **AI-assisted semantic triage layer**. The rule-based classifier alone is insufficient for production promotion decisions.

### 10.2 Future AI-Assisted Triage Requirements

**AI triage responsibilities**:
- Classify whether a candidate is: ordinary feeling, durable inference, factual note, relationship fact, academic fact, negative capability inference, or high-risk claim.
- Estimate: factuality, durability, usefulness, risk, recurrence, privacy_level, and stability.
- Produce a structured JSON recommendation with `recommended_action`, `risk_level`, `unsafe_inference_detected`, and human-readable `reason`.
- Explain *why* a candidate should be `short_term_auto_write` / `medium_factual_auto_commit` / `manual_review` / `auto_reject_or_expire` / `keep_pending`.

**AI triage constraints** (hard rules that AI cannot override):
- Must NOT commit high-risk memory.
- Must NOT update core_blocks.
- Must NOT decide final truth about the user.
- Must NOT infer relationship status from ordinary emotional expressions.
- Must NOT infer ability/personality from grades or academic stress.
- Must NOT diagnose health or mental health conditions.
- Must NOT bypass the policy resolver.

**Future AI triage prompt principles**:
- Do not convert temporary feelings into durable identity facts.
- Do not infer relationship status from ordinary emotional expressions.
- Do not infer ability/personality from grades or academic stress.
- Do not diagnose health or mental health.
- Do not auto-commit high-risk facts.
- Return JSON only.

**Future AI triage output schema** (proposed):
```
recommended_action, memory_type, factuality, durability, usefulness,
risk_level, privacy_level, suggested_ttl_days, should_commit_long_term,
review_required, unsafe_inference_detected, reason
```

**Future eval examples**:
- "我想她了" → short_term_auto_write
- "我现在很难受" → short_term_auto_write
- "这件事让我自我否定" → short_term_auto_write / emotional_observation
- "用户长期因为 Ellie 自我否定" → manual_review
- "CSC165 51，STA237 68" → medium_factual_auto_commit
- "用户学习能力差" → auto_reject_or_expire
- "用户被诊断为焦虑症" → manual_review
- third_party_doc infers preference → auto_reject_or_expire

### 10.3 Policy Architecture

Final decision architecture: **hard rules + AI triage + policy resolver**

- **Hard rules** (type gates, source_trust gates, provenance gates): enforce non-negotiable safety boundaries.
- **AI triage**: provides semantic classification and confidence estimation.
- **Policy resolver** (`classify_candidate_review_policy()` evolved): makes the final action decision by combining rules with AI triage output.
- **User review**: reserved for high-risk or ambiguous durable memory only.

## 11. Explicit Non-Goals

- No Web UI for review queue or short-term observations.
- No health-derived mood inference (health data stays in health pipeline).
- No high-risk auto-commit (`identity_fact`, `health_baseline`, `risk_flag`, `policy_rule`).
- No long-term personality diagnosis.
- No automatic relationship fact inference.
- No `health_baseline` or `risk_flag` auto-write.
- No `core_blocks` auto-update.
- No Provider Boundary Policy implementation (deferred to Phase 1.6).
- No `memory_items` primary retrieval switch (deferred to post-Phase 1.4 shadow eval).
- No changes to Hermes actor scope or permissions.
- No changes to Telegram bot architecture.
- No changes to existing `resolve_candidate()` rules until dry-run validation is complete.
